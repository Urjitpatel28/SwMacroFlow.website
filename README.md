# swmacroflow.in

The SwMacroFlow website: a static marketing page, the download block, and the legal pages for the
Windows desktop application.

Plain static HTML, no framework and no package manager. **Pushing to `main` deploys to
production**: `.github/workflows/static.yml` uploads the repository root to GitHub Pages, so any
`.html` at the root becomes a live route on the next push.

There is one generator, `tools/build-site.mjs`, and it has no dependencies. It exists because the
guides and the macro library used to be fetched and rendered in the browser, which meant twelve
pages of content lived at two URLs and none of it was indexable. It now writes a page per guide and
per macro ahead of time. See [Generated pages](#generated-pages).

## Generated pages

```bash
node tools/build-site.mjs
```

Requires Node 20 or newer for the built-in `fetch`. It reads `docs/manifest.json` and `docs/*.md`
locally, fetches `library-index.json` and `Docs/*.md` from the public
`Urjitpatel28/SwMacroFlow.MacroLibrary` repository, and writes every generated file in the table
above.

**The output is committed.** That is what keeps `python -m http.server` a full preview of the site
with no build. The Pages workflow regenerates before deploying anyway, so a stale commit cannot
reach production — it only warns.

Things worth knowing before changing it:

- **Markdown is rendered by `assets/markdown.js`**, the same file the browser and the desktop app
  use, evaluated in Node. A build-time page is therefore character for character what the old
  client-side reader produced. Do not swap in a Markdown library.
- **Titles and descriptions come from `tools/seo-meta.json`**, keyed by slug. A page with no entry
  falls back to its own H1 and first paragraph, so a new guide never breaks the build — it just
  gets a weaker title until someone writes one.
- **`HelloWorld` is excluded** from the macro pages. It is a one-line test fixture in the library
  repo, and a page for it would be thin content beside five real ones.
- **The workflow also runs weekly** (Mondays, 05:00 UTC). The macro library lives in its own
  repository, so a macro published there reaches the site without a commit here.
- **`library-index.json` arrives double-encoded** — an em dash comes through as `â€”`. The build
  repairs it and logs when it does. Fixing it upstream would let that code go.

Images are separate and manual, because they are committed binaries and rebuilding them on every
push would produce a diff on every push:

```bash
python tools/build-images.py   # needs Pillow
```

## Access model

**There isn't one.** SwMacroFlow is free, every feature is included, and the site has no accounts,
no licence keys, no activation, and no payments. The installer is linked publicly from the home
page and anyone can download it.

This is deliberate and the copy depends on it: `index.html`, `terms.html`, and `privacy.html` all
state plainly that there is nothing to buy and nothing to sign up for. If a paid tier is ever
reintroduced, all three have to change together — and the privacy policy in particular, because it
currently promises no device identifier and no account data of any kind.

AI Copilot is **bring your own key**: the user supplies an API key from a provider they choose, that
provider bills them directly, and the key never leaves their machine. That is the one cost the user
may incur, and it is not ours to charge or refund.

## Updating the docs

`docs/*.md` are a **manual one-way copy** of `SwMacroFlow.Ui\Resources\Help\*.md` from the application
repository. That repository is private, so the guides cannot be fetched from GitHub at runtime the way
the macro library is — they have to live here.

When the application's help guides change, copy the files across again, **run `node tools/build-site.mjs`**,
and commit both. If a guide is added, removed, or reordered, also edit `docs/manifest.json` so its groups
and order still match `HelpLibrary.Groups` in `SwMacroFlow.Ui\Services\HelpLibrary.cs`. Page headings come
from each document's first `#` heading, the same rule the application uses.

Two of those headings are overridden for the site in `tools/seo-meta.json`: `01-overview.md` opens
`# SwMacroFlow`, which is right inside the application's help pane and useless as a page title and a
sidebar label. A new guide needs a `tools/seo-meta.json` entry too, or it ships with a title derived
from its own H1.

## Publishing a release

`release.json` at the repo root is the single description of the current build. The download block
on `index.html` reads it through `assets/release.js`, and **the application's auto-updater should
verify every download against the same `sha256`** before running it — that is the check that
actually protects users, not an installer hashing itself.

Installers are published as GitHub releases on the **public** `Urjitpatel28/SwMacroFlow.Releases`
repository. The application repository itself is private, and release assets on a private repo are
not publicly downloadable — a link to one 404s for everybody.

`url` in `release.json` is GitHub's stable latest-release permalink and **never needs changing**:

```
https://github.com/Urjitpatel28/SwMacroFlow.Releases/releases/latest/download/SwMacroFlowSetup.exe
```

For each release:

1. Publish a GitHub release on `SwMacroFlow.Releases` with the installer attached, named exactly
   `SwMacroFlowSetup.exe` so the permalink resolves.
2. Get its checksum: `Get-FileHash .\SwMacroFlowSetup.exe -Algorithm SHA256`
3. Fill in `release.json` — `version`, `sha256` (64 hex chars), `sizeBytes`, `releasedOn`
   (`YYYY-MM-DD`).
4. Push to `main`.

The download block goes live when `url` and `version` are both non-empty; until then it shows a
"coming shortly" message. `sha256` is displayed only when it is a valid 64-character hex string —
a wrong checksum is worse than none, because it makes a good file look tampered with, but a missing
one is no reason to withhold the download.

Clicking Download opens a thank-you dialog carrying the **SmartScreen warning**. The installer is
unsigned, so Windows shows "Windows protected your PC" to anyone without an EV certificate's
reputation behind them; a user who has not been warned reads that screen as "this is malware" and
never runs it. If code signing is ever added, that dialog is the thing to revisit.

## Testing locally

```bash
node tools/build-site.mjs     # only if docs/ or the macro library changed
python -m http.server 8000
```

Then open `http://localhost:8000`. Check pages over `http://`, not by opening files directly:
`index.html` fetches `release.json` and the reviews section calls Supabase, and browsers block those
on `file://`. The guide and macro pages no longer fetch anything — their content is in the HTML.

Worth checking after a change to the generator:

```bash
python -c "import xml.dom.minidom; xml.dom.minidom.parse('sitemap.xml')"   # sitemap still parses
curl -s http://localhost:8000/docs/writing-a-macro/ | grep -c '<h2'        # content is in the HTML
```

The second one is the check that matters. If it ever returns 0, the site has regressed to where it
started: pages whose content only exists after JavaScript runs.
